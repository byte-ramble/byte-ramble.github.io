Wallet Transaction Provenance Standard

WTP 是钱包交易构造溯源标准：让软钱包负责交易构造，让硬件钱包或独立设备负责离线复核，用厂商签发的 envelope 交叉校验交易字节、目标链与来源。

BEHAVIOR FLOW

从交易构造到签名前复核

WTP 把“谁构造交易、谁出示、谁验证、何时联网、何时签名”拆成明确步骤，适配软钱包、硬件钱包和任意第三方 verifier 的交叉校验。

01 Construct

软钱包构造交易

钱包、插件或 Safe 提案端生成 raw transaction、SafeTxHash 或 Solana message；UI 只是展示层，权威输入是可编码交易字节。

02 Envelope

封装 WTP envelope

写入 wire namespace、payload_hash、chain / cluster、有效期和 vendor_sig，把构造来源与交易字节绑定到同一个 envelope。

03 Present

通过 wtp1 通道出示

QR、NFC、图片或文本都只是传输载体；通道可被替换，但替换后的内容会在 hash、chain 或 origin 校验中暴露。

04 Verify

独立设备本地复核

Verifier 或硬件钱包使用 pinned roots 与已验签 metadata 校验来源，重新计算 payload_hash，并恢复链上下文。

05 State

按需补充链上状态

Safe nonce、EVM 合约代码、Solana ALT 和模拟结果由伴随设备或独立 RPC 提供，只作为可复核输入，不作为信任锚。

06 Decision

签名或拒绝

当 Bytes、Chain、Origin 以及必要状态检查全部通过后，硬件钱包或用户才输出签名；任一失败则拒绝。

SIGNING RISKS

常见签名风险

真正的问题是“看到的”和“签名的”之间被插入了不可信代码。WTP 通过可验证 envelope，把交易字节、链上下文与来源签名放回同一个离线验证流程里。

Front-end Tampering

前端渗透

浏览器扩展、dApp 前端、桥接器或剪贴板被 XSS、供应链攻击、恶意插件改写后，UI 展示的是一笔交易，实际签名的是另一笔。

Blind Signing

盲签

复杂 calldata、Permit、SafeTx 嵌套让钱包很难独立判断目标链、目标地址、授权范围与金额。

Origin Spoofing

来源伪造

二维码、深链、推送都可能被替换；没有厂商签名时，来源是否真是该钱包无法被密码学判定。

CORE PROPOSITION

每一笔待签交易都应该携带厂商签发的 envelope

钱包厂商用 Vendor Root 到 QR Signing Cert 的信任链签发 WTP envelope。任何持有 trustedRoots 与最近一次有效 trust metadata 的用户、第三方安全公司、审计或研究者，都能离线验证来源与交易字节是否被改过。

01 · Wallet Vendor

签发权威字节

签名对象是 canonical transaction bytes，而不是截图、页面文案或二维码图像。

02 · Anyone

独立校验真伪

独立设备可重算 hash、恢复 chainId 或 cluster，并验证厂商签名。

PRINCIPLE

一个 envelope 同时回答三个问题

Bytes · Chain · Origin。任一验证失败，envelope invalid。

Q1 · Bytes

交易字节是否被改？

从 envelope 恢复原始 RLP、typed transaction 或 Solana message，重算 payload_hash，并与声明值比对。

Q2 · Chain

目标链是否匹配？

EVM 从字节本身恢复 chainId；Solana 用 envelope 声明 cluster，并与策略里的 expectedChainId 或 expectedCluster 对齐。

Q3 · Origin

QR 来源是否可信？

从本地信任根验证 QR Signing Cert，再验证 detached COSE_Sign1 over canonical transaction bytes。

TRUST MODEL

Vendor Root → Cert → Sign

公开分发渠道不是信任锚。WTP 的信任锚来自本地信任根；trust metadata 本身用 root_sig 模式自签，revoked_at 在验证器同步到新的已签名 metadata 后生效。

01

Vendor Root

本地信任的钱包厂商根公钥指纹 sha256(SPKI_DER)，作为离线验证信任锚；首次安装时应通过应用包、固件包、手工指纹核对或企业策略完成 pinning。

02

QR Signing Cert

由 Vendor Root 签发，绑定 QR 签名公钥与 key_id；验证器从已签名的 trust metadata 中读取证书、有效期和吊销状态。

03

COSE_Sign1 over tx

对 canonical_CBOR(tx) 做 Ed25519 detached 签名；签的是权威交易字节，不是 QR 图像或 UI 文案。

TRUST METADATA LOOP

信任根、metadata 与吊销的闭环

WTP 的离线验证不是无条件相信二维码，而是相信本地已初始化的 Vendor Root，以及最近一次同步且通过 root_sig 验证的 trust metadata。

Bootstrap

信任根初始化

Verifier 首次安装时内置或导入 trustedRoots，并展示 Vendor Root 指纹供用户、企业策略、硬件钱包固件或审计流程确认。公开分发渠道只负责传递文件，不自动成为信任根。

Distribution

Trust Metadata 获取

厂商发布 metadata，包含 root_fingerprint、signing cert、key_id、有效期、revoked_at 与 root_sig。验证器可从官方发布渠道或企业策略渠道获取，但必须先验 root_sig。

Revocation

离线吊销边界

revoked_at 不是让离线设备凭空感知吊销。它只会在验证器同步到新的已签名 metadata 后立即生效；纯离线模式使用最后一次同步的 metadata，并应显示 metadata 时间戳和过期/过旧警告。

State Checks

独立 RPC 的职责

Bytes、Chain、Origin 三项可在本地完成；独立 RPC / 模拟用于查询 nonce、Safe 状态、ALT 内容、合约代码和余额变化。需要实时链上状态时才联网，且联网结果不能替代厂商签名。

CROSS VERIFICATION

不同应用和不同设备都可以交叉验证

出示方可以是不可信通道；验证方可以是另一台设备、另一个应用、硬件钱包或第三方 verifier。只要本地持有可信根、已验签 metadata 和可复核链上状态，就能基于 WTP 对同一张 QR 做无许可独立验证。

SOFTWARE + HARDWARE WALLET

补上硬件钱包无法独立离线验证的短板

传统硬件钱包擅长保护私钥，但在复杂 calldata、SafeTx、Permit 或跨链交易里，常常只能显示有限字段，无法判断来源是否可信。WTP 把软钱包的交易构造能力和硬件钱包的隔离签名能力接成一个可验证流程。

软钱包出示权威 envelope

手机或桌面钱包负责构造交易、签发 WTP QR，并把 raw bytes、payload_hash、chain / cluster 和 vendor_sig 一起交给硬件钱包或独立验证器。

硬件钱包离线复核

硬件钱包不信任宿主机 UI，只信任本地 pinned roots 和最近一次同步的 signed metadata；扫码后本地重算 hash、验签、解码展示，再决定是否输出签名。

联网状态由伴随设备承担

硬件设备保持隔离；伴随手机或桌面端只同步 metadata、链上状态和模拟结果。硬件端把这些作为可验证输入，不把联网通道当作信任锚。

COVERAGE

覆盖 EVM 与 Solana

同一个 envelope 模型覆盖 EVM 与 Solana 交易，并兼容 Safe 离线签名、vendor_sig 来源认证等上层签名场景。

EVM 广播交易

  • legacy / EIP-155 typed bytes
  • EIP-2930 access-list tx
  • EIP-1559 dynamic fee tx
  • EIP-4844 signed tx body + blob versioned hashes
  • EIP-7702 authorization list / tuples

EVM Safe 离线签名

  • SafeTxHash QR
  • Safe address + chainId + nonce
  • owner 离线签名
  • EOA / eth_sign 恢复核对
  • replay 防护状态校验

Solana message / 已签交易

  • legacy message
  • v0 versioned transaction
  • Address Lookup Table
  • vendor_sig 认证 cluster
SCENARIOS

WTP 的典型使用场景

01

大额转账二次确认

主钱包发起后出示 WTP QR，用户用第二台独立设备扫码；字节、地址、金额、链 ID 与厂商签名同时一致才继续确认。

02

Safe 多签收集签名

提案方钱包出示 SafeTx QR，其他 owner 在各自设备上离线扫码、离线签名，签名收齐后再链上提交。

03

第三方安全审计

安全公司、审计与研究者在本地 pin 住厂商根后，可用公开 trust metadata 离线判定任意 WTP envelope 是否由该厂商签发、字节是否一致。

04

硬件钱包冷签

在线设备出示待签 QR，硬件钱包或冷端扫码后重算 hash、验厂商签名、解码展示并输出已签 QR，解决硬件钱包只能盲签、无法独立验证来源的问题。

SUMMARY

无许可独立验证

WTP v1 定义钱包交易构造溯源的公开验证模型；在本地信任根、已验签 metadata 和独立设备复核链路未同时失效时，验证流程可以显著降低静默欺骗风险。
